**会议主题**：黄仁勋Demo开发与产品定位对齐会
**发言人**：贺梁琪、郭毅芙
**会议摘要**：本次会议明确了Demo采用“数值驱动”与“纯对话驱动”双轨并行策略，确立了基于“黄仁勋”分支的敏捷开发规范，并澄清了项目非游戏化、面向Z世代轻量互动的产品定位。
---
### 一、Demo 开发策略与机制设计
针对 Demo 的剧情推进机制，双方就技术实现路径与交互体验进行了深度对齐：
#### 1. 剧情推进的双轨并行机制
- **双线驱动策略**：决定采用“数值驱动”与“纯对话驱动”两条路径并行。数值驱动便于基于规则调整，而纯对话驱动则适用于轻量级前端展示，避免过度游戏化。
- **明暗数值系统**：采纳“明线（可见数值）”与“暗线（隐藏数值）”结合的设计。明线作为用户交互依据，暗线作为实际推动故事发展的核心逻辑，以提升故事沉浸感。
#### 2. Agent 行为与边界优化
- **边界条件限制**：针对 Agent 在初始设置中缺乏边界限制的问题，后续需增加对用户恶意输入或偏离主线的行为进行警告或拒绝执行的逻辑。
- **AI 痕迹消除**：针对当前 Agent 回答中存在破折号过多、AI 味过重的问题，需通过优化 Prompt 和系统提示词（System Prompt）来提升自然度。
### 二、代码管理与开发规范
为解决当前代码结构混乱及功能堆叠问题，制定了明确的代码分支管理策略：
#### 1. 分支管理策略
- **独立开发分支**：建立名为“黄仁勋”的独立分支用于 Demo 开发，严禁直接推送到 main 分支。开发人员可在该分支上进行大改，不受限制。
- **Feature 抽象与提交流程**：要求每 1-2 天进行一次 Feature 提炼，若功能足够抽象且必要，可直接提 PR；若不够抽象，需与团队共同重构后再提交。
#### 2. 代码结构优化
- **功能内化**：批评当前所有功能堆叠在 Flask 应用层的做法过于臃肿，要求将 Feature 内化到引擎底层，保持代码的轻量化与可维护性。
### 三、产品定位与团队分工
贺梁琪对项目整体方向提出疑问，郭毅芙详细阐述了项目的非游戏属性及最终愿景：
#### 1. 产品形态与竞品定位
- **非游戏化定位**：明确项目并非传统游戏，而是介于短视频/图文阅读之上增加轻量级对话互动的媒介。核心目标是吸引 Z 世代用户，提供新颖的互动体验。
- **最终形态愿景**：Demo 旨在验证底层引擎的 Feature，最终目标是实现“Video Jam”形态，即动态视频结合气泡对话，为后端游戏 NPC 提供 Agent 化基础。
#### 2. 团队开发线划分
- **三大板块并行**：目前团队分为三大板块，分别是网站开发（2人）、黄仁勋 Demo（贺梁琪负责）以及“杀戮尖塔”逆向工程（用于投资人体验）。
